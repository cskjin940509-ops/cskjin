# 数据到达后的计算与发布

后台原先主要由各自的五分钟定时任务串接。GitHub Actions 使用 GITHUB_TOKEN 提交的数据不会触发普通 push 工作流，因此上游已经发布时，下游仍可能等待下一轮 cron。

现在所有主要生产数据发布调用 `tools/publish_data_on_arrival.py`：数据有变化才提交，提交成功后并行调用固定下游的 workflow_dispatch，始终读取 main 最新数据。既有定时任务保留，供采集和事件通知失败时补漏。没有新增交易账户或实际券商下单。

| 数据完成 | 立即发生的工作 |
|---|---|
| 网关核心行情完成校验 | 先发布，再通知影子账户、交易计划、执行辅助；尾盘和日终任务按时段通知 |
| Yunai 独立确认完成 | 补充发布，再通知相同下游；未取得独立确认时原有交易门槛仍生效 |
| 慢资金采集完成 | 先发布并通知雷达，再生成开盘前预测池；盘中独立重试日频数据补采 |
| 雷达、交易引擎与账本契约校验完成 | 原子发布雷达与账户，再更新和发布同期收益基准 |
| 正式池实时交易计划完成 | 先发布，再运行全 A 历史形态补充筛选 |
| 尾盘核心结果完成 | 先发布并通知计划与执行辅助，再补充独立确认 |
| 日终正式池完成 | 发布后通知计划、执行辅助与收益跟踪，不等待历史收益计算 |
| 收益跟踪或历史证据修复完成 | 发布后立即通知历史形态实验室，不必等到 16:45 |

只有相应数据发生变化才通知。研究数据周末修复也能触发研究重算；涉及交易的事件按工作日、交易时段分流，各消费者继续检查真实交易日、行情时间、双源确认、T+1、集合竞价及策略门槛。五分钟 slot 作为原有策略记录口径保留，不能靠重复事件重复买卖。

慢资金不再阻塞实时采集；原有四个自然日的有效期上限保留，过期或缺失时清除旧 B1/B2/B4 确认及分数字段，显示不可用。它不会被替换成零值或伪造通过。

日终收益跟踪在 15:00 后，若当天已审核冻结快照中至少四个核心指数具有 15:00 及以后的最终行情时间，可立即开始。证据不足时保留原 15:20 安全窗口；个股收益仍由原有多源验证脚本决定是否可计算。

同一任务及雷达/账户共享串行队列，运行中的生产任务不被新通知取消。多个等待通知由 Actions 队列合并为最新待运行任务，开始时重新读取 main。发布使用普通快进推送，远程无关改动可重放；同一数据发生冲突时停止，不覆盖新账本、不通知下游。发布及通知时间、耗时、提交 SHA 和失败对象记录在每次工作流的 Step Summary；通知失败会明确使步骤失败，已成功发布的数据仍保留。

验证包含临时 Git 仓库的原子发布、删除/新增文件、并发数据冲突、无变化不通知、独立下游故障隔离、无环事件图、发布顺序、收盘证据门槛，以及原有持仓/底仓 T/研究回归测试。合并后 `Verify production data dispatch` 用真实 GITHUB_TOKEN 调起只读测试工作流，验证运行环境确实支持显式触发。

## 延迟边界

这次去掉的是数据计算后等待下一轮定时器、等待非必要研究完成的延迟。上游行情获取仍采用轮询，外部服务响应、GitHub runner 排队、必需的双源核验和账本串行提交仍有耗时。不能承诺逐笔行情或秒级时效。要实现持续接收行情、到达即计算，需要常驻服务和可靠的行情推送接入，不能仅靠 GitHub Actions 的 cron。

参考：[GitHub 工作流触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)，[GitHub 定时事件与延迟限制](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
